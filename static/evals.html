Question-by-question results

Evaluation methodology
  • The questions. 50 fixed questions about decisions, votes, dissents, topics, year comparisons, follow-ups, reworded versions of the same question, and meetings whose minutes are not public yet. Code generates them (tests/make_key.py), so every model gets the identical set.
  • Who decides the right answer. No person and no AI. The answer key comes from the Fed's minutes: each meeting's decision, target range and vote are read out of the minutes text by code, and those readings were checked against the actual change in the federal funds rate for all 150 meetings (tests/testDecisions.m).
  • Who grades the answers. Code, not a person or an AI judge. Each answer is checked with fixed text patterns: the right direction (raised, cut or held), the right rate range, the right dissenters' names, or "not public yet" wording for unreleased meetings. A question counts as correct only if every check matches.
  • What the grader cannot see. Because it reads text, an unusual but correct phrasing can be marked wrong. Topic and comparison questions only check for the topic words or both years, so a high score there is lenient. The 4 "why" questions have no key and are not scored; they only feed the invented-reason flag.
  • Baseline. The same Ollama model and context size, given only the question and the date: no tools, minutes, data, guardrail or citation check. "One agent" is everything we add around the model: the lookups, the point-in-time guardrail and the checks, all handled by one model conversation.
  • Multi-agent. The same checks, split across specialists as in docs/agents.md: code routes the question, the minutes and market agents each look up and report on their own part (each with its own prompt and only its own tools), the scorer and consumer agents run when the question needs them, the writer reads their reports, and a critic checks the draft (one rewrite at most). It runs on the same model and questions as the one-agent run, so any difference is the architecture. A specialist's report that adds a number or paragraph id its sources lack is replaced by the code's own text.
  • Tokens and cost. Tokens are counted by Ollama over every model call in a question (the lookups, the answer and the citation check), averaged over all 50 questions. The models run locally, so the real cost is $0. "API cost" is what those same tokens would cost on a paid cloud model at its list price (Claude Haiku 5.5 and Sonnet 5.5, list prices checked on the Anthropic pricing page), with no caching discount. It is an estimate of the order of magnitude: a cloud model counts tokens with its own tokenizer. Questions the app refuses before calling the model (not public yet) cost $0, and a baseline follow-up counts only its last turn.
  • Limits. One run per model per question (the one-agent runs were made earlier than the multi-agent runs), on one 8 GB Apple M1, so run-to-run variation is not measured. Every score is out of 46, so differences of a few points are not meaningful.

Lookahead methodology
  • What is tested. The FOMC minutes agent of this project (fomc-minutes-llm), as one whole: the tools, data cutoff, guards and prompts around a model. Every run uses the same model inside it, the app's default, so the stages differ only in what is around the model.
  • The three stages. Baseline = the app with the data cutoff off: the tools can return anything, the date the model is told is today's, and the as-of date is only said in the question. Guards = the app as it is in main: data cut off at the as-of date, dated lookups refused, checks on the answer, and the prompt rule never to use memory of later events. Guards plus prompts (v1) = the same app with the point-in-time rules from agents/shared/asof.md in the writer's prompt, every specialist's prompt and the date line of the first message: a later meeting, month or value is "not known yet", never guessed, and general knowledge of later events is not used even when the user asks. The rules were written from the types of question, not from the answers that went wrong.
  • Who decides the right answer. Code. The rate decisions, target ranges and unemployment values come from the data files (the target-range series and the first release of each month); the 20 event questions use a hand-written list of events and the dates they became public. A model is never the judge.
  • What counts as an error. An answer that presents something after the as-of date as known: it states the later fact (a sentence with the decision and its range, the later range, the later value, or the event's name, not given by a tool in guarded runs), or, for a question about one fact, it gives a value instead of saying it is not known on that date. An invented value counts, because the model ignored the date. Event questions are open, so only stating the event counts there.
  • Controls. 10 questions about decisions that were public by their as-of date. The answer must give the decision and range. This catches a model or a guard that refuses everything.
  • Held out. 20% of each family was set aside before any prompt work, so a prompt tuned on the rest can be checked on questions it was not tuned on.
  • Limits. One run of one model, so run-to-run variation is not measured. Whether an answer declines is read from its wording, so an unusual phrasing can be misjudged either way. The patterns for stating a later fact cover only the facts in the key. The baseline's control questions fail because the small model often ignores a date given only in the question, which says the baseline is weak, not that it knows the future. Training cutoffs of the models are assumed from their release dates, not confirmed.
