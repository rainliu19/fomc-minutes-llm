Question-by-question results

Evaluation methodology
  • The questions. 57 fixed questions about decisions, votes, dissents, topics, year comparisons, follow-ups, reworded versions of the same question, and meetings whose minutes are not public yet. Code generates 50 of them (tests/make_key.py) and 7 forward-looking ones were written by hand, so every model gets the identical set.
  • Who decides the right answer. No person and no AI. The answer key comes from the Fed's minutes: each meeting's decision, target range and vote are read out of the minutes text by code, and those readings were checked against the actual change in the federal funds rate for all 150 meetings (tests/testDecisions.m).
  • Who grades the answers. Code, not a person or an AI judge. Each answer is checked with fixed text patterns: the right direction (raised, cut or held), the right rate range, the right dissenters' names, or "not public yet" wording for unreleased meetings. A question counts as correct only if every check matches.
  • What the grader cannot see. Because it reads text, an unusual but correct phrasing can be marked wrong. Topic and comparison questions only check for the topic words or both years, so a high score there is lenient. The 4 "why" questions have no key and are not scored; they only feed the invented-reason flag.
  • Baseline. The same Ollama model and context size, given only the question and the date: no tools, minutes, data, guardrail or citation check. "One agent" is everything we add around the model: the lookups, the point-in-time guardrail and the checks, all handled by one model conversation.
  • Multi-agent. The same checks, split across specialists as in docs/agents.md: code routes the question, the minutes and market agents each look up and report on their own part (each with its own prompt and only its own tools), the scorer and consumer agents run when the question needs them, the writer reads their reports, and a critic checks the draft (one rewrite at most). The critic verifies facts in code against the decision card (the vote, the direction, the target range, a bare paragraph id or an empty reply) and, if the rewrite still fails, the answer is composed from the card itself; the tables count those answers as "from code". One agent has no such critic. It runs on the same model and questions as the one-agent run, so any difference is the architecture. A specialist's report that adds a number or paragraph id its sources lack is replaced by the code's own text.
  • Tokens and cost. Tokens are counted by Ollama over every model call in a question (the lookups, the answer and the citation check), averaged over all 57 questions. The models run locally, so the real cost is $0. "API cost" is what those same tokens would cost on a paid cloud model at its list price (Claude Haiku 5.5 and Sonnet 5.5, list prices checked on the Anthropic pricing page), with no caching discount. It is an estimate of the order of magnitude: a cloud model counts tokens with its own tokenizer. Questions the app refuses before calling the model (not public yet) cost $0, and a baseline follow-up counts only its last turn.
  • Limits. One run per model per question, all three structures run on the same day with the same code, on one 8 GB Apple M1, so run-to-run variation is not measured. Every main-key score is out of 53 and every held-out score out of 36, so differences of a few points are not meaningful. The held-out key (36 questions on meetings, topics and wordings the first key never uses) was added after the multi-agent checks were built on the first key. Five models' multi-agent runs on the main key predate the critic's target-range check, which can only improve them.

Lookahead methodology
  • What is tested. The FOMC minutes agent of this project (fomc-minutes-llm), as one whole: the tools, data cutoff, guards, code checks and prompts around a model. Every run uses the same model inside it, the app's default, so the stages differ only in what is around the model.
  • Baseline. The app with the data cutoff off: the tools can return anything, the date the model is told is today's, and the as-of date is only said in the question. No guards, no prompt rules.
  • v0: guards. The app as it is in main: data cut off at the as-of date, dated lookups refused, checks on the answer, and a meeting whose minutes are not public yet is answered "not public" by code, without the model.
  • v1: guards, a date check and prompt rules. v0 plus two additions. (1) A date check in code: when a question names a period the data cannot show yet, the app answers "not known as of the anchor date" itself, with the latest known value and its date, without asking the model. A period is a month in words ("June 2020", "July of 2020", "February 1, 2023"), a quarter ("Q2 2021"), a part of a year ("the end of 2021"), or a distance from the anchor date ("3 months from now", "next quarter"); a period the data shows, a question about forecasts, or no period named goes to the model as before; a question about a rate decision or vote at a meeting whose minutes are not public is answered the same way. (2) Short point-in-time rules from agents/shared/asof.md in the writer's prompt, every specialist's prompt and the date line: nothing after the anchor date, even if the user asks for general knowledge. Most of the drop from v0 to v1 is the date check (see "Answered by code"), not changed model behaviour. It cannot read a month with no year, a numeric month ("9/2019"), a season, a bare year or "the next meeting", and a decision question with no rate or "decide" word may still reach the model.
  • The question sets. The lookahead error rate pools two sets: the unseen set, written after v1 was built and never used to develop it, and the fresh set, the same kinds of facts in wordings the main key never uses. The fresh set was also used to find gaps in v1's date check, so the unseen set alone is the cleanest test of v1. The baseline and v0 were fixed before any of the sets existed, so their rates are fair. When v1 is changed after seeing a set's errors, that set is no longer a fair test and a new one is written. The earlier narrower v1 (month names only) is kept in evals/lookahead/archive/.
  • Who decides the right answer. Code. The rate decisions, target ranges and unemployment values come from the data files (the target-range series and the first release of each month); the event questions use a hand-written list of events and the dates they became public. A model is never the judge.
  • What counts as an error. An answer that presents something after the as-of date as known: it states the later fact (a sentence with the decision and its range, the later range, the later value, or the event's name, not given by a tool in guarded runs), or, for a question about one fact, it gives a value instead of saying it is not known on that date. An invented value counts, because the model ignored the date. Event questions are open, so only stating the event counts there.
  • Controls. Questions about facts that were public by their as-of date (a decision, an unemployment value, a target range). The answer must give the fact. This catches a model or a guard that refuses everything; a failure is usually the small model garbling a number, not a refusal.
  • Limits. One run of one model per stage, so run-to-run variation is not measured, and the pooled 118 questions still give a wide range (shown). Whether an answer declines is read from its wording, so an unusual phrasing can be misjudged either way. The patterns for stating a later fact cover only the facts in each set. The baseline's control questions fail because the small model often ignores a date given only in the question, which says the baseline is weak, not that it knows the future. Training cutoffs of the models are assumed from their release dates, not confirmed.
